# Parts library

Generated by `npx tsx scripts/parts/report.ts`. How a part gets in: [the part check](../scripts/parts/check.ts) (wiring, design checks, breadboard plan, simulator example + test on ESP32 and Pico, KiCad footprint, a routed DRC-clean circuit board, LCSC stock) and then [publish](../scripts/parts/publish.ts), which compares the part with a blind second reading of the datasheet (header pin order, roles, I2C address, supply range, conversion constants, chip ID). Any disagreement goes to review instead of the library.

**Nothing here has been tested on real hardware yet.** "Checked" means the simulator, the circuit-board tools and two independent datasheet readings agree.

## Didn't make it

| Part | Outcome | Why |
|---|---|---|
| MS5611 | unsupported | The MS5611 returns both D1 (pressure) and D2 (temperature) from the same ADC-read command 0x00, chosen by the preceding one-byte conversion command (0x40-0x48 vs 0x50-0x58). The i2c-device sim can't do this: a bare command byte stores no register data, so measure.when can't see it, and a 'responses' reply is cleared by the 0x00 write the real driver must send. D1 also depends on both temperature and pressure through the PROM compensation, which the per-control linear measures can't encode. |
| Capacitive soil moisture sensor v1.2 | duplicate | lookup.ts reports the part is already in Sparkbench as built-in 'soil' (Capacitive soil moisture sensor); nothing added. |
| DS18B20 waterproof probe | duplicate | scripts/parts/lookup.ts reports 'Already in Sparkbench: part-ds18b20'; the waterproof probe is the same DS18B20 1-Wire chip, so no new part was added. |
| WS2812B strip 30 | duplicate | lookup.ts reports 'Already in Sparkbench: neopixel-ring (NeoPixel ring (12x WS2812B))'; that built-in is the same WS2812B chip with a configurable 'pixels' LED count prop (set to 30) and 'led strip' keyword, same 5V/GND/DIN wiring. |
| WS2812B 8-LED stick | duplicate | lookup.ts reports 'Already in Sparkbench: neopixel-ring (NeoPixel ring (12x WS2812B))'; the built-in WS2812B part has a configurable 'pixels' LED-count prop (GND/VCC/DIN/DOUT), so an 8-LED WS2812B stick is covered by setting pixels=8. |
| WS2812B single | duplicate | lookup.ts reports the WS2812B is already in Sparkbench as built-in part neopixel-ring (NeoPixel ring (12x WS2812B)), matched on the WS2812B MPN; stopped per step 1. |
| TMP1075 | not-found | No widely sold TMP1075 hobbyist breakout exists (no Adafruit, SparkFun, MikroE Click, Qwiic/STEMMA, Tindie or common clone module); the only board is TI's TMP1075EVM, a USB stick with an MSP430 whose snap-off sensor tab has an unpopulated 5x2 header (J3), so there is no real single-row header pin order to model. |
| Capacitive soil moisture sensor v2.0 | duplicate | scripts/parts/lookup.ts reports the part is already in Sparkbench as built-in 'soil' (Capacitive soil moisture sensor); no new part was created. |
| LM335 | unsupported | The LM335 is a 2-terminal shunt (zener-like) sensor that only regulates to 10 mV/K (2.98 V at 25 C) when an external bias resistor sets 0.4-5 mA through it; Sparkbench's analog-sensor is a supplied voltage source with a fixed 1 kOhm output impedance, so a declared bias pullUp forms a divider that shifts readings by tens of degrees, and omitting it makes the sim work where the real circuit reads ~0 V (a power-role pin would short the part across the supply). Its 2.73-3.73 V output also exceeds a 3.3 V ADC in the usual 5 V bias circuit, so it cannot be modelled faithfully. |
| AM2302 | duplicate | lookup.ts reports the part is already in Sparkbench as built-in 'dht22' (DHT22 temperature & humidity); the AM2302 is the wired DHT22, so no new part was added. |
| FS90R | unsupported | The FS90R is a continuous-rotation servo: per the Feetech spec the 700-2300 us pulse sets speed and direction (1500+/-45 us stop, 90 us dead band, CW below / CCW above, no limit angle), but the Sparkbench 'servo' sim kind only maps pulse width to a held arm angle (0..degrees), and no other kind models motor speed/direction, so modelling it would show a false fixed position. Not built; no check run. |
| PCF8575 | unsupported | The TI datasheet requires every transfer to be pairs of bytes, with byte 1 setting P07-P00 and byte 2 setting P17-P10. The simulator's pointerless I2C model (GenericI2CDevice.write in src/sim/devices.ts) keeps only the LAST written byte in register 0x00, so a real two-byte write would drop port 0 and put port 1's data on P00-P07. No existing sim option can model a 16-bit two-port pointerless latch faithfully without bending the driver to the simulator. |
| TMP75 | not-found | No widely sold TMP75 (TI SBOS288) hobbyist breakout exists: no Adafruit, SparkFun, Qwiic/STEMMA, Grove, Tindie or common clone module; the only TMP75 breakout found is an unsold Hackaday.io hobby project (Dave's Dev Lab, no published pin order), and MikroE Thermo 22 Click (MIKROE-5068) uses the TMP75C, a different chip with its own datasheet (SBOS707, 1.4-3.6 V, fixed 12-bit) on a 2x8 mikroBUS layout, so modelling it as a TMP75 would be wrong. |
| TMP112 | not-found | No widely sold hobbyist TMP112 breakout with a pin header exists (searches of Adafruit, SparkFun, Seeed, DFRobot, Waveshare, Pimoroni, MikroE, AliExpress/Amazon/Tindie found only TMP102/TMP117 boards); the only commercial board, NCD's TMP112 I2C Mini Module, is out of stock, costs about $42, uses two 4-pin nodeLynk 5 V bus connectors with a PCA9306 level shifter and jumper pull-ups to the 5 V bus, so it is not a beginner breadboard part. The TMP112 is register-compatible with the TMP102, which is already in Sparkbench (part-tmp102). |
| ENS210 | unsupported | ENS210 returns T_VAL/H_VAL as 3 bytes: 16-bit data little endian, a VALID bit (bit 16) and a CRC-7 (poly 0x89, init 0x7F) over those 17 bits in bits 23:17; the simulator has no CRC-7 segment or measure checksum (only 8/16-bit CRCs on whole bytes), so it cannot produce the real readout bytes a datasheet-correct driver checks. Not faked. |
| CM1106 | unsupported | The CM1106 UART reply (16 05 01 DF1 DF2 DF3 DF4 CS) uses checksum CS = 256 - (HEAD+LEN+CMD+DATA) % 256, summed over every byte including the 0x16 head (datasheet example 16 05 01 02 58 00 00 8A). The simulator's ResponseSegment checksums (sum8, sum16, neg16, mhz19, modbus16, sensirion, htu21d, xor8hex) have no 8-bit negated sum over all bytes: 'mhz19' leaves out the first byte and 'neg16' is 16 bits. A faithful frame can't be built without faking the reserved DF4 byte, so the chip was not modelled. |
| ILI9488 | unsupported | Over its 4-line SPI interface the ILI9488 takes pixels only as 3-bit or 18-bit RGB666 (3 bytes per pixel, COLMOD 0x3A 0x66; datasheet section 4.7.2 gives only those two SPI formats, and 16-bit RGB565 does not work over SPI on real modules), but the Sparkbench tft-display model (TFTDevice in src/sim/devices.ts) decodes RAMWR 0x2C data as 2-byte RGB565 pairs only. A correct driver would show up as a garbled screen in the simulator, and a driver sending RGB565 to suit the simulator would fail on real hardware. |
| SSD1351 | unsupported | The SSD1351 uses its own command set (Set Column 15h and Set Row 75h with one-byte 7-bit addresses, Write RAM 5Ch, display on/off AFh/AEh), but the tft-display sim (TFTDevice in src/sim/devices.ts) only understands MIPI DCS 2Ah/2Bh/2Ch/28h/29h/36h, so a correct SSD1351 driver would draw nothing in simulation, and a driver shaped to the sim would not work on the real chip. |
| HT16K33 alphanumeric | unsupported | The simulator's ht16k33 segment-display decodes one RAM byte per digit as a 7-segment glyph (segText uses bits a-g only), but a 14-segment alphanumeric digit uses 16 bits across two RAM bytes (split G1/G2 middle, diagonals, centre verticals), so real 14-segment font data (e.g. '3' = 0x008F, letters like M/W/K) cannot be represented or read back faithfully. Modelling it would require shaping the driver to 7-segment glyphs, which is not allowed. |
| HT16K33 8x8 matrix | unsupported | The simulator's segment-display protocol ht16k33 (HT16K33Device + engine.ts) only decodes the RAM bytes listed in digitMap as 7-segment glyphs into segText; it never produces pixels, and the matrix flag is honoured only for max7219, so an 8x8 HT16K33 matrix would be shown and tested as fake 7-segment digits. No part files were written; a faithful model needs an ht16k33 matrix mode (8 rows x 8 columns from RAM bytes 0,2,...,14 into v.pixels). |
| MAX7219 4-in-1 matrix | unsupported | The 4-in-1 module is four MAX7219 chips daisy-chained DOUT->DIN, but the simulator's max7219 segment-display model (MAX7219Device) is a single chip: on LOAD it keeps only the last 16 bits shifted in and renders one 8x8 matrix, so the other three chips' frames and 24 of the 32 columns cannot be modelled faithfully. The existing part-max7219-8x8-matrix skill (FC-16, same VCC/GND/DIN/CS/CLK header) already has a driver with num=4 for this strip. |
